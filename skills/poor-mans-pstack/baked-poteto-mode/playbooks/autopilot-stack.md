# Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear base-branch stack to review and land.** For "autopilot-stack", "stack them, don't ship", "build the stack, I'll land it", and executing a plan that **Multi-phase plan** ([multi-phase-plan.md](multi-phase-plan.md)) wrote.

1. **Run the owner loop.** Use GitHub CLI (`gh`) for every PR operation. Never require Graphite (`gt`). One owner works the PRs in dependency order and owns each change end to end: build, the first push, a ready PR opened before self-proof, self-proof on the real artifact ([Prove It Works](../../principle-prove-it-works/SKILL.md)), the **deslop** skill, and the **no-comments** skill. The owner is the main session inline, or one delegate at a time spawned as your configured `feature`, `refactoring`, or `bug-fix` agent (the **Subagents** section of the entry skill) in its own worktree. Never run two owners at once. Within about 15 minutes of starting a PR, the owner pushes its first branch snapshot and opens the PR ready, never draft. Open the PR before self-proof so the URL and checks form a durable trail. The owner does the first rebase before the code-ready report, whether or not trunk has drifted. In fix rounds, the owner keeps that merge base. The owner rebases again only at stack prep, on a `git merge-tree` conflict with trunk, or on a CI failure that comes from a change on trunk. Before a push that starts a round, run the pre-review checks that the repo's AGENTS.md files and rules name for the touched paths. Run them on the committed head. A hook pass is not proof. Read CI at each pushed head with `gh pr checks <pr>` and fix what fails. A watch that polls CI until green is a long loop. Tell the operator the expected cost and get a go-ahead first. To publish each rebase, push the owner's own branch with `git push --force-with-lease` after an `ls-remote` check. Never force-push a shared branch.
2. **Audit at every PR boundary.** Before the owner starts each PR, re-read this playbook and the plan file. Audit the operation against both. Fix drift before the next PR starts. With a delegated owner, the harness notifies you when it returns. Count only side effects as progress: commits, pushes, and PR or check deltas. Treat an owner that errors, or that passes its expected runtime without a side effect, as stuck. Stop it, confirm it stopped, and dispatch a fresh owner with consolidated scope. A stall never proves or drops the work.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. The statement names the expected cost, the PR count and the verification rounds, because the run is long and unattended. Start only on the operator's explicit go. The plan file carries the program objective across turns. On the operator's stop, the owner takes an immediate zero-writes hold and keeps its brief until the operator releases it.
4. **Verify each round.** The owner reports its code-ready head SHA once the shipped code is final, after the deslop pass and the no-comments pass, and the SHA of each later push that changes the patch. It reports STACK-READY with the exact head SHA when its loop is green. A round starts at the code-ready head SHA and at each later push that changes the patch. The root runs these lanes at that SHA and aggregates them to one verdict.
   - Re-run the gates at that SHA.
   - Prove the load-bearing behavior live on the real surface the change touches. Drive it directly with the project's verification skill, the built-in `run` skill, or a named driver where neither fits. The live lane is the floor, and a verdict without it is not clean.
   - **Regression lane against trunk.** Run the same load-bearing scenario on current trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for instead of pretending trunk can produce it.
   - Audit the diff, distrusting the PR body. Run the **interrogate** skill with the full brief. Give the brief the main focuses, such as consumer parity with trunk, lifetimes and races, or data and config safety.

   Audit the receipts in the STACK-READY report before the verdict. When the lanes return, send every proven finding against the PR to the owner in one fix-forward. A defect that a lane filed as a note is a finding. For each behavior finding, ask for a red test that covers every site with the same defect. Where no test can show the defect, ask for a repro receipt instead. Add that defect to the next round's review brief. The new head gets a fresh round and a fresh verdict, except for lane results that stay valid under the patch-id rule in step 7. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear base-branch stack, in verified order or an order the operator specified.
6. **Single writer on topology.** The owner pushes only its own branches and reports the tip, the current base, and the intended parent. The root is the only topology writer. To append a PR, fetch the intended parent, rebase the child branch onto that exact parent tip, push with `--force-with-lease` only after an `ls-remote` check, and set the PR base to the parent branch. Create it with `gh pr create --base <parent-branch>`. Retarget an existing PR with `gh pr edit <pr> --base <parent-branch>`. Only the root PR targets trunk. Never submit or register the chain through `gt`.
7. **Absorb drift at the root, then re-verify what moved.** The root fetches current trunk and rebases the chain from bottom to top. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice and the root pushes the result. A rebase rewrites every SHA above it and voids verdicts at the old SHAs. Apply the patch-id rule at each verdict SHA. Anything that is no longer valid goes back through step 4 before delivery. Re-run mergeability and CI after every rewritten push even when the patch-id is unchanged. A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) stops for the operator's approval. Absorbing values that already landed on trunk is drift, not a raise.

   **Patch-id rule.** Record the verdict head SHA, the base SHA, and the `git patch-id --stable` of that PR's base-to-head diff. Before delivery, compare the recorded patch-id with the current base-to-head patch-id. When the patch did not change, keep the code verdict but re-run mergeability and CI at the current head. When the two patches differ only in tests, docs, or lint config, build what each lane ran. Build it twice at the verdict SHA and once at the current head. A difference is noise if the two builds at the verdict SHA also show it, or if it is an embedded commit SHA. Judge each difference, not each file, and report each kind of noise with its files. If only noise differs, that lane's result stays valid, and checks and a review of the change run fresh. Do not reuse a lane result from a dev server or from anything else with no build output. Rerun that lane. Re-verify anything else when the patch changed. Never use matching commit messages or a green check from an older SHA as a substitute.
8. **Deliver the chain.** The deliverable is one linear chain of verified PRs, reviewable bottom-up in GitHub, every link carrying its verdict in the PR body or a comment. The operator reviews and lands it, with their own clicks or by arming merge-when-ready.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.
